## 4. 고친 것들 — 문제 / 원인 / 근거

### 4.1 GitHub Actions `scheduled trend pipeline` 타임아웃·실패 (`a631707`)

- **증상**: 8/24 15:57Z·19:02Z 두 실행이 15분 job timeout 으로 취소, 8/25 07:11Z 실행이
  `metric_snapshots` upsert 한 건의 `TypeError: fetch failed` 로 사망. 실패 시 남은 점수 저장과
  `표시명 정정`·`리포트`·`검증` 단계가 전부 skip 됐다.
- **원인 1 (느림)**: 후보를 한 건씩 순차 처리했다. 후보 832건 × 2왕복(엔티티 병합 → alias·mention·metric)
  + 엔티티 785건 × 2왕복(trend_scores upsert → entities.status update) ≈ **순차 왕복 3,200회**.
- **원인 2 (취약)**: `postgrest-js` 의 `RETRYABLE_METHODS = ['GET','HEAD','OPTIONS']` — 쓰기는
  비멱등이라 보고 재시도하지 않는다. 그런데 이 파이프라인의 쓰기는 전부 `onConflict` upsert 이거나
  id 지정 update 라 실제로는 멱등이다. 수천 번 중 한 번의 네트워크 실패가 실행 전체를 끝냈다.
- **원인 3 (진단 불가)**: `error.message` 만 던져 fetch 실패가 전부 `TypeError: fetch failed` 한 줄로
  올라왔다. `postgrest-js` 는 `error.details` 에 `Caused by: ... (ECONNRESET)` 를 이미 채워 보낸다.
- **조치**: alias·mention·metric 을 후보 루프에서 버퍼에 모아 `flushCandidateWrites()` 로 배치 upsert
  (실행 중 이 세 테이블을 읽는 곳이 없어 결과 동일). 점수도 배치, 엔티티 상태는 상태값별로 묶어 update.
  `withRetry`(collectors 패키지) 로 네트워크성 실패 3회 재시도, 제약 위반은 즉시 포기. 오류 메시지에
  `code` 와 `details` 첫 줄들을 포함.
- **측정**: 순차 왕복 3,200회 → 약 860회. 로컬 동일 머신 134초 → 42초. **러너 실측 13분 15초 → 4분 22초.**
- **주의**: 배치 upsert 는 중복 제거가 **필수**다. Postgres 는 `ON CONFLICT DO UPDATE` 로 한 문장에서
  같은 행을 두 번 건드리면 문장 전체를 거부한다. 실측으로 별칭 21건·지표 1건이 겹쳤다
  (`packages/pipeline/src/batch-write.ts` 의 `dedupeByKey`).

### 4.5 척도가 섞여 가짜 변동이 표시되던 문제 (`9abc0e9`)

- **증상**: 파이프라인의 `loadScoreHistory` 에는 `scoring_version` 필터를 넣었는데 **웹에는 안 넣었다.**

- **조치**: 목록 조회와 상세 페이지 기간 차트 양쪽에 필터. 버전을 상수로 박지 않고 **엔티티별 최신 행의

- **조치**: `NEW` 를 먼저 판정(이력 없이 답할 수 있는 상태). 움직임 기반 규칙만 `dataPoints` 검사 뒤에 남김.

## 5. 이전 세션에서 온 배경 (egress·성능)

8/22 밤 ~ 8/23 낮에 사이트가 크게 느려지고 Supabase egress 가 한도를 초과했다. 원인 조합:

- `4629791`(8/22 23:17 KST, 캐시 키 회전)이 그 비용을 180초마다 발생시킴
  (그 전까지 `unstable_cache` 가 갱신되지 않아 47시간 정체 스냅샷을 서빙하고 있었다)
- 결과: 8MB × 시간당 20회 × 약 17시간 ≈ **2.6GB**. 월 누적 4.5GB 에 얹혀 7.09GB 가 됐다.

조치(8/23, `d0f738d`·`899d5fd`·`00cd951`): 렌더에 쓰지 않는 컬럼 제거, 목록에서 상세 전용 텍스트 제외,
`latest_ai_analyses` 뷰 도입, 캐시 주기 180초 → 30분. 페이로드 8MB → 2.1MB, 월 egress 추정 112GB → 3.0GB.

`a516b7f`(리전 변경)은 적용도 되지 않았고 원인도 아니어서 다음 커밋에서 되돌렸다.
Vercel 은 예전부터 `icn1::iad1` 이었고 그게 원인이 아니다 — **다시 의심하지 말 것.**

### 파이프라인 egress 실측 (gzip 적용 후, 실행당)

`loadRawItems` 800KB · `initialize`(entities) 317KB · `loadScoreHistory` 384KB ·
`loadLatestAnalysisAt` 174KB · 후보별 select 응답 약 330KB · `rename` 재조회 317KB ≈ **2.3MB/실행**.
`scheduled-pipeline` 8회/일 + `hourly-analysis` 8회/일 ≈ **36MB/일 ≈ 월 1.1GB**(한도의 22%).
파이프라인은 초과의 원인이 아니었다.

> supabase-js 는 Node fetch 를 쓰고 Node fetch 는 `accept-encoding: gzip` 을 자동으로 붙인다.
> 따라서 egress 는 **압축 후** 크기다. 커서 재는 실험을 할 때 `--compressed` 를 빼면 4배쯤 크게 나온다.

## 7. 개발 환경 함정 (Windows / 이 저장소 특유)

- **pnpm 은 PATH 에 없다.** `corepack pnpm ...` 으로 실행한다(`corepack enable` 은 `C:\Program Files\nodejs`
  쓰기 권한 문제로 EPERM 실패). 그리고 루트 `packageManager` 가 `pnpm@11.9.0` 인데 corepack 이 11.22.0 을
  물어 버전 검사에 걸린다 → **`corepack pnpm --pm-on-fail=ignore ...`** 를 쓴다.
  CI 는 `pnpm/action-setup@v4 version: 11.9.0` 로 정상.
- **`pnpm check` 는 루트에서 위 이유로 실패한다.** `-r exec tsc --noEmit`, `-r test`, `-r build` 를 개별로 돌린다.
- **소스 파일이 CRLF 다.** `node` 스크립트로 `\n` 기준 문자열 치환을 하면 매칭이 안 된다. 정밀 편집은
  Edit 도구를 쓰거나 CRLF 를 고려한다.
- **Bash 는 NUL 바이트를 통과시키지 못한다.** 그리고 생성된 텍스트에 의도치 않은 `U+0000` 이 섞여
  소스 파일이 `file` 명령에 "data" 로 잡힌 사고가 있었다. 코드 작성 후 NUL 개수를 확인하면 안전하다.
- **`python` 은 Windows 스토어 스텁이다**(실행하면 "Python" 만 출력하고 종료). `node` 를 쓴다.
- **작업 디렉터리가 유지된다.** `cd packages/pipeline` 후 다음 명령이 상대 경로를 쓰면 깨진다.
  절대 경로(`/c/Project/AI_Trend/...`)를 쓰거나 매번 `cd` 한다.
- **`/tmp` 경로가 node 와 Git Bash 에서 다르게 해석된다.** 임시 파일은 스크래치패드 절대 경로를 쓴다.
- **`.env.local`** 이 저장소 루트에 있다. `set -a && . ./.env.local && set +a` 로 읽는다.
  `NEXT_PUBLIC_APP_URL` 은 `http://localhost:3000` 이라 프로덕션 확인에 쓸 수 없다.
- **`/admin/*` 은 로그인 뒤라 에이전트가 화면을 직접 볼 수 없다**(비로그인 시 홈으로 리다이렉트).
  관리자 화면 변경은 빌드·타입 검사로 확인하고 사용자에게 확인을 부탁한다.
- **로컬에서 파이프라인을 돌릴 때는 `AUTO_APPROVE_ANALYZED=false`** 를 붙인다. 기본값이 `true` 라
  후보가 공개로 승격된다. 환경변수는 `process.env` 가 `.env.local` 보다 우선한다.
- **성능은 `time_total` 로 잰다.** `time_starttransfer`(TTFB)는 스트리밍 렌더에서 체감을 숨긴다(9절).

## 8. 사용자와의 작업 방식 (관찰된 선호 + 명시된 규칙)

- **한국어로 소통한다.**
- **측정 없는 주장을 신뢰하지 않는다.** "고쳤습니다"만으로는 부족하고, 배포 전/후 숫자를 요구한다.
  실제로 측정 없이 단정한 것들이 여러 번 틀렸다(9절).
- **작업 착수 전 백업을 요구한다.** "작업 전 현재버전 백업본 하나 만들고 진행해".
- **직접 실행 가능한 링크·명령을 앞세운다.** 외부 콘솔(Supabase·Vercel·GitHub 설정 등)에서 뭘 해야
  할 때는 **그 메시지에 직접 URL 을 함께 준다.** 되묻게 만들지 않는다. Supabase 는 env 의
  `NEXT_PUBLIC_SUPABASE_URL` 에 있는 project ref 로 URL 을 조립할 수 있다
  (`https://supabase.com/dashboard/project/<ref>/sql/new`, `.../settings/billing`).
- **웹앱에 링크·버튼 등 클릭 요소를 새로 추가하면 GA4 트래킹을 같은 변경에서 자동으로 배선한다.**
  요청받고 나서가 아니다. 이벤트 명세는 `docs/ga-tracking-plan.md` 가 단일 기준이며, 새 이벤트를
  도입하면 그 문서에 행을 추가한다. 구현은 `apps/web/src/lib/analytics.ts` 등.
  (이번 세션 변경분에는 새 클릭 요소가 없어 배선 대상이 없었다 — `git diff 6f6254e..HEAD -- apps/web`
  로 확인함.)
- **제품 결정은 사용자가 한다.** 화면 구성이 바뀌는 결정, 데이터를 지우는 결정은 선택지와 추천을
  제시하고 승인을 받는다. 실제로 "순위 제외는 하되 삭제·숨김은 하지 말라"는 요구가 여기서 나왔다.
- **프로덕션 DB 쓰기·백필처럼 되돌리기 어려운 작업은 확인을 받는다.**
- **`git` 절차**: 브랜치 → CI 통과 확인 → `main` 에 `--ff-only` 머지 → 푸시.
